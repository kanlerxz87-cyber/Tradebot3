1. Objective and scope

Tradebot3 is a static, GitHub-Pages-hosted dashboard for live Kalshi prediction markets restricted to five topics: gas prices, elections, culture, crypto and golf. Within each topic it ranks live events by official Kalshi contract volume, watches every contract for sudden moves of $0.10 or more in either direction, follows events until Kalshi settles them, and provides a paper-trading and strategy-testing environment on real quoted prices.

The design rule for the whole build is simple: a displayed number must trace to an official API field or be an explicitly labelled calculation. Where that was impossible, the value is blank and listed on the Flagged for review page.

2. Verified API architecture

  • Market data — production, unauthenticated. https://external-api.kalshi.com/trade-api/v2 (recommended host) for /series, /markets, /events/{ticker}, orderbooks and candlesticks. Source: API environments.
  • Demo account — optional, read-only. https://external-api.demo.kalshi.co/trade-api/v2 for GET /portfolio/balance, signed in the browser with RSA-PSS. Source: Demo environment, API keys.
  • Orderbooks return bids only; implied asks come from the $1.00 binary reciprocal (YES ask = 1 − best NO bid). Source: Orderbook responses.
  • Candlesticks support only 1-minute, 1-hour and 1-day periods, 5,000 periods per request. Source: Get Market Candlesticks.
  • WebSockets need the same KALSHI-ACCESS-* headers in the handshake, which a browser page cannot set — the reason this build polls REST. Source: WebSocket quick start.

3. What the dashboard does

  1. Highest-dollar live events. Events are ranked by official contract volume with a clearly labelled dollar estimate; each row links to the Kalshi event page and the raw API record.
  2. Two live alert chats. One feed shows every ≥ $0.10 move detected from Kalshi's 1-minute candles and from live polls; the second shows only moves whose market also passes a transparent 0–100 screen (liquidity 40, spread 20, price band 15, catalyst 15, runway 10).
  3. Chart with jump markers. X axis is time (live seconds, 1m, 5m, 15m, 1h, 6h, 1d), Y axis is the contract price in dollars. Every ≥ $0.10 move is plotted; clicking a marker opens the Kalshi event page and the topic's official primary sources, labelled as candidates rather than causes.
  4. Liquidity ladder. Resting contracts and dollar value at each of the ten best levels per side, with implied asks, spread and depth totals. Clicking a level loads that size into the ticket.
  5. Resolution tracking. Open events are followed until Kalshi publishes result and settlement_value_dollars; the resolution tables record YES/NO outcomes, settlement value and volume, and open paper positions settle automatically at $1.00 or $0.00.
  6. Paper portfolio and strategy lab. $10,000 simulated account with fills at real book prices, trade categorisation, P&L by category/topic/side, an equity curve, four strategy backtests on real candles, and an optional live auto-trader that reacts to ≥ $0.10 alerts.

4. Data pipeline and verification

A GitHub Actions workflow (.github/workflows/refresh-data.yml) runs every 20 minutes. It discovers the five topics' series through GET /series, fetches markets, orderbooks and candles, derives swing alerts, collects recent settlements, re-checks the previous dataset's 29 claims against the live API, and commits a compact assets/data/snapshot.json. The site reads that file and then polls the public API every 20 seconds for live ticks. scripts/verify_site.py checks internal links, topic isolation, source coverage and the snapshot schema before every publish.

5. Audit result (most important finding)

The previous build's market catalogue was largely unverifiable. Of its 29 claimed Kalshi markets, most do not exist in the live production API, and the prices/volumes attached to them could not be reproduced from any official endpoint. Those rows have been removed and replaced with API-sourced markets. The full row-by-row result — claimed value, live lookup outcome, HTTP status of the claimed link — is published on Flagged for review and in legacy-audit.json.

Also removed: invented model “fair values”, invented “observed swings”, and news links presented as the causes of specific price moves. The replacement model reports its component scores and asserts nothing about the future.

6. Risks and limitations

  • No authenticated streaming in the browser — 20-second polling, not tick-by-tick. A server relay is the fix.
  • CORS is undocumented — live polling may be blocked on GitHub Pages; the UI reports the actual state and falls back to the snapshot.
  • Demo ≠ production — measured divergence is published; demo is used only for a read-only balance check.
  • Contract volume, not dollar volume — the dollar column is an estimate.
  • Small samples — roughly two hours of 1-minute candles per market; backtests are illustrative, gross of fees.

7. Recommendations

  1. Stand up a small server-side WebSocket relay (Cloudflare Worker) so the dashboard can stream ticker, trade, orderbook_delta and market_lifecycle_v2 with instant resolution banners.
  2. Add browser notifications and an audio ping for model-qualified moves, with per-topic thresholds.
  3. Extend the paper engine to limit orders with depth-weighted fills, then to demo order placement once the order schema and CORS route are verified.
  4. Publish a calibration view: after a ≥ $0.10 move, how often does price retrace by topic and by liquidity bucket?
  5. Persist alerts for multi-day history so the “sudden swing” threshold can be evaluated over weeks, not hours.
