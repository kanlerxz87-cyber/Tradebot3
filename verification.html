2. API behaviour verified line by line

TopicWhat the official documentation saysHow this site uses itOfficial source
Authentication Three headers: KALSHI-ACCESS-KEY, KALSHI-ACCESS-TIMESTAMP (milliseconds), KALSHI-ACCESS-SIGNATURE. The signature is base64 over timestamp + METHOD + path, with query parameters stripped. Ed25519 keys sign directly; RSA keys use RSA-PSS with SHA-256 and salt length equal to the digest length. Timestamps must be within 30 seconds. Portfolio page signs GET /portfolio/balance with Web Crypto RSA-PSS (salt 32) from a key you paste in; nothing is stored. API Keys
Public market data The orderbook endpoint states that “no authentication is required”. This site's snapshot job calls GET /series, GET /markets, GET /events/{ticker}, GET /markets/{ticker}, orderbook and candlesticks without credentials. Data pipeline uses only unauthenticated endpoints. Orderbook
Orderbook shape orderbook_fp contains yes_dollars and no_dollars arrays of [price_dollars, count_fp]. Arrays are ascending; the best bid is the last element. Only bids are returned: YES ask = $1.00 − best NO bid, NO ask = $1.00 − best YES bid. Unknown tickers return HTTP 200 with empty arrays, not 404. Liquidity ladder derives implied asks and the spread with exactly those formulas. Orderbook responses
Candlesticks GET /series/{series_ticker}/markets/{ticker}/candlesticks with period_interval ∈ {1, 60, 1440} minutes. One request may span at most 5,000 periods; start_ts/end_ts must be seconds. The most recent candles can lag trades by a few seconds. Chart uses 1m and 60m candles; the “Live · sec” view is built from browser polling ticks and is labelled as such. Candlesticks
WebSockets Connections require the same three auth headers in the handshake, signed over timestamp + "GET" + "/trade-api/ws/v2". ticker, trade and market_lifecycle_v2 carry public market data but still use the authenticated session; orderbook_delta, fill, market_positions, communications, order_group_updates and user_orders are private. Not used directly: a static page cannot set handshake headers. The site polls REST every 20 s instead and flags the limitation. WebSocket quick start
Rate limits Token-bucket budgets per read and write bucket; most requests cost 10 tokens; a throttled request returns 429 with too_many_requests and X-RateLimit-* headers. Unauthenticated public requests have separate limits. Snapshot job sleeps between calls and backs off on 429/5xx; the browser polls at most 40 tickers every 20 seconds. Rate limits
Demo vs production Demo uses mock funds and separate credentials; Kalshi states “the price and behavior of markets in the demo environment may not be reflective of those in real markets”. Market data is production; the demo connection is only for reading your demo balance. The divergence is measured and published. Demo environment
Historical data Markets settled before the historical cutoff expose candles only via GET /historical/markets/{ticker}/candlesticks. Resolution tables rely on the market result/settlement_value_dollars fields, not on old candles. Historical data

5. How paper fills and settlement work

  • Entry price: the YES/NO ask you can actually pay — from the 20-second live quote when one has arrived, otherwise the last orderbook snapshot. If neither exists the last trade price is used and the trade records price_source so the fallback is visible.
  • Mark: the bid for the side you hold (never the ask), so unrealised P&L already carries the spread. The chart panel labels whether a quote is a live quote or a snapshot.
  • Settlement: when Kalshi publishes result = yes/no, an open position pays $1.00 if the side matches and $0.00 otherwise, and moves to the closed log with the reason “resolved YES/NO”. The result is read from the market record or, once the contract leaves the open-market list, from the resolution table — both are Kalshi's own field, and the trade records which one answered (settlement_source). Without that fallback a position in a settled market would stay open forever.
  • Fees: excluded everywhere, and labelled as gross, because the fee schedule is not reproduced from an official source in this project.
  • Storage: the account lives in this browser's localStorage. Export produces a JSON file; reset restores $10,000.

8. Automation — how the data stays current, and how often it actually runs

Scheduled refresh. .github/workflows/refresh-data.yml asks for a run every 30 minutes (cron */30 * * * *) and on demand. It executes scripts/fetch_kalshi_data.py, which discovers the five topics' series through GET /series, pulls markets, orderbooks and 1-minute/1-hour candles, derives ≥ $0.10 alerts, collects recent settlements, re-audits the legacy claims, checks every official link, and commits the result as assets/data/snapshot.json. The page you are on reads that file and then polls the same public API for live ticks.
Delivered cadence is slower than the cron. GitHub Actions throttles scheduled workflows, so the interval that is requested is not the interval that runs. The job appends every run to assets/data/refresh-history.json and the snapshot publishes the measured gaps (refresh_cadence) — see the figures below. The dashboard shows the snapshot's age, so a slow refresh is visible instead of being described as “live”.

9. Suggestions to make the dashboard more live and interactive

  1. Server-side WebSocket relay. Deploy a small Cloudflare Worker or Node service that holds the authenticated wss://external-api-ws.kalshi.com session (it can sign the handshake) and fan out ticker, trade, orderbook_delta and market_lifecycle_v2 to browsers over SSE. This removes the 20-second polling delay and unlocks true sub-second charts.
  2. Instant resolution banners. Subscribe to market_lifecycle_v2 so a resolved event flips from “open” to YES/NO within seconds, and auto-settle paper positions at that moment.
  3. Push alerts and sound. Add Web Notifications plus an optional audio ping for model-qualified ≥ $0.10 moves, with per-topic thresholds and a quiet-hours toggle.
  4. Orderbook ladder trading. Clicking a depth row already loads a ticket; the next step is a limit-order form with a depth-weighted fill estimate and a “walk the book” preview showing how many contracts are available at each price.
  5. Catalyst calendar. Pin scheduled official releases (EIA Weekly Petroleum Status Report, AAA daily fuel gauge, AP election calls, PGA TOUR leaderboards, crypto settlement benchmarks) as vertical markers, and mark a detected move as “near scheduled release” instead of guessing causality.
  6. Event-driven feed framing. Group alerts by event rather than by contract, so one news shock that moves eight strikes shows as a single thread with the full repricing.
  7. Calibration and persistence. Store every alert in IndexedDB, then publish a calibration view: after a ≥ $0.10 move, how often did the price retrace 50% within an hour, by topic and by liquidity bucket?
  8. Shareable state. Encode the selected market, timeframe and filters in the URL, add keyboard shortcuts (j/k to move markets, 1–6 for timeframes) and a compact mode for a second monitor.

10. Limitations and flagged items

  • Demo prices and volume differ from production; the snapshot includes a measured spot check.
  • Public API contract volume is not dollar volume; the dollar figure on the dashboard is an estimate.
  • Orderbook snapshots are point-in-time (ten levels per side) and refresh with the snapshot, not tick-by-tick.
  • Browser CORS may block direct calls to Kalshi from GitHub Pages; the live badge reports this honestly.
  • Everything that could not be confirmed is listed on Flagged for review.
